Section 1

Pourquoi l'Architecture d'Entreprise ?

Avant d'apprendre la méthode et le langage, il faut comprendre le problème qu'ils résolvent. Tout part d'une tension fondamentale dans les organisations.

1.1 Le problème : des processus transversaux, des applications cloisonnées

Les processus métier (chapitre 3 !) ont besoin des services des systèmes d'information pour s'exécuter : enregistrer une commande dans une base de données, récupérer un dossier client, calculer un prix…

Mais il y a un décalage structurel :

  • Les SI sont organisés par domaine fonctionnel : une application pour les ventes, une pour la comptabilité, une pour les RH… Ce sont des applications cloisonnées (« silos »).
  • Les processus métier sont transversaux : traiter une commande traverse les ventes, la logistique, la facturation…

1.2 Le lien avec le chapitre 1 : l'alignement stratégique

🔗 Lien avec le chapitre 1
Le cours réactive ici le modèle d'alignement stratégique de Henderson & Venkatraman : 4 quadrants (Stratégie commerciale, Stratégie IT, Infrastructure organisationnelle, Infrastructure IT), reliés par le fit stratégique (vertical : stratégie ↔ opérations) et l'intégration fonctionnelle (horizontal : métier ↔ IT). L'alignement dit quoi viser ; il ne dit pas comment y arriver concrètement.

En pratique, l'alignement se réalise via une multitude de projets (chacun avec son cycle requirements → analysis → design → implementation → test, cf. chapitre 2). Sans vision d'ensemble, ces projets partent dans tous les sens. Il faut un instrument de coordination global : c'est l'Architecture d'Entreprise.

1.3 Définition de l'Architecture d'Entreprise (EA)

📖 Définition (à connaître — slide 11)

L'EA est un ensemble cohérent de descriptions qui fournit des indicateurs et des contrôles permettant une gouvernance éclairée de l'évolution et du succès de l'entreprise.

L'EA est un instrument qui permet d'articuler l'orientation future d'une entreprise, tout en servant de mécanisme de coordination et de pilotage vers la transformation effective de l'entreprise.

En clair : l'EA, c'est modéliser l'entreprise entière (métier + applications + technologie) pour piloter sa transformation de façon cohérente — plutôt que projet par projet, silo par silo.

💡 Pour retenir
L'EA joue pour toute l'entreprise le rôle que le BPM (ch. 3) joue pour un processus : décrire l'existant (as-is), concevoir la cible (to-be), et piloter la transition. D'ailleurs, les 5 qualités d'un modèle du chapitre 1 (abstrait, compréhensible, précis, prédictif, peu coûteux) s'appliquent aussi aux modèles d'architecture !
✏️ Vérifie ta compréhension
1. Quel est le décalage fondamental qui motive l'Architecture d'Entreprise ?
✔ Exactement : SI en silos verticaux, processus horizontaux. C'est ce croisement qui crée les problèmes d'intégration que l'EA veut maîtriser.
2. Vrai ou faux : « L'EA remplace le modèle d'alignement stratégique de Henderson & Venkatraman. »
✔ Faux : l'EA opérationnalise l'alignement. Le modèle H&V donne la vision (fit stratégique + intégration fonctionnelle) ; l'EA est l'instrument qui coordonne les projets pour la réaliser.
3. Dans la définition de l'EA, quels sont les deux rôles clés de l'instrument ?
✔ Les deux verbes de la définition : articuler (dire où on va) et coordonner/piloter (y aller de façon cohérente).
Section 2

La méthode TOGAF et son cycle ADM

TOGAF = The Open Group Architecture Framework. C'est la méthode (le « comment faire ») la plus utilisée pour pratiquer l'architecture d'entreprise.

2.1 Pourquoi TOGAF ?

Le cours donne 7 arguments (slide 12) — retiens-en l'esprit : c'est un standard ouvert, neutre et éprouvé :

  • Basé sur les meilleures pratiques
  • Neutre vis-à-vis des fournisseurs (pas lié à un éditeur de logiciels)
  • Norme ouverte avec documentation ouverte
  • Évite de réinventer la roue
  • Adaptable aux normes industrielles
  • Largement adopté
  • Complémentaire avec d'autres cadres (dont… ArchiMate !)

2.2 Le cycle ADM (Architecture Development Method)

Le cœur de TOGAF est un cycle itératif de phases. Clique sur chaque phase de la roue pour découvrir son contenu 👇

Clique sur une phase

La roue ADM

Les phases A → H s'enchaînent en boucle (démarche itérative, comme le cycle de vie BPM du chapitre 3). La Gestion des exigences est au centre : elle alimente toutes les phases en continu. Note le code couleur : B = métier 🟡, C = SI 🔵, D = technologie 🟢 → ce sont exactement les 3 couches d'ArchiMate !

2.3 Le pattern commun des phases B, C, D : as-is → gap → to-be

Les trois phases d'architecture (métier, SI, technologique) suivent la même logique en 3 temps — c'est un grand classique d'examen :

L'analyse de gap identifie 4 types de lacunes (slide 16) :

  • Gaps dans les processus
  • Gaps dans les personnes (compétences)
  • Gaps financiers
  • Gaps matériels
💡 Lien avec le chapitre 3
Tu reconnais la logique ? C'est la même que le cycle de vie BPM : découvrir le processus actuel (as-is) → analyser → redesign (to-be) → implémenter → monitorer. Et la migration Baseline → Transition(s) → Target rappelle la roue PDCA : on avance par étapes intermédiaires qu'on peut « fêter ».
✏️ Vérifie ta compréhension
1. Où se situe la « Gestion des exigences » dans le cycle ADM ?
✔ Les exigences sont identifiées, stockées dans un référentiel et intégrées dans toutes les autres phases. D'où sa position centrale dans la roue.
2. Remets dans l'ordre : quelle phase vient juste après « B. Architecture métier » ?
✔ B → C → D suit la logique descendante des couches : métier d'abord, puis SI qui le supporte, puis technologie qui supporte le SI. Exactement l'ordre des couches ArchiMate.
3. Une entreprise compare son architecture actuelle à son architecture visée et découvre que ses employés n'ont pas les compétences pour le nouveau CRM. De quoi s'agit-il ?
✔ Comparer as-is et to-be = analyse de gap. Les compétences manquantes = gap dans les personnes (un des 4 types : processus, personnes, financier, matériel).
Section 3

ArchiMate : le langage et ses 3 couches

TOGAF dit comment procéder ; ArchiMate dit comment dessiner. Sans langage commun, chaque couche utiliserait sa propre notation (BPMN pour les processus, UML pour les applis, schémas réseau pour l'infra…) — impossible de voir les liens entre couches.

📖 À retenir
ArchiMate est un langage de modélisation unifié pour l'architecture d'entreprise, maintenu (comme TOGAF) par l'Open Group. Il est complémentaire à TOGAF : la roue ADM structure la démarche, ArchiMate exprime les modèles produits par les phases B, C et D.

3.1 Les 3 couches (définitions exactes du cours — slide 40) ★★★

CoucheDéfinition du cours
Couche métier
(Business)		 Propose des produits et services à des clients externes, mis en œuvre dans l'organisation par des processus métier exécutés par des acteurs métier.
Couche des systèmes d'information
(Application)		 Soutient la couche métier avec des services d'application mis en œuvre par des applications (logicielles).
Couche technologique
(Technology)		 Propose des services d'infrastructure (traitement, stockage, communication) nécessaires au fonctionnement des applications, mis en œuvre par du matériel informatique/communication et des logiciels système.
💡 La logique verticale
Chaque couche sert celle du dessus via des services : la technologie sert les applications, les applications servent le métier, le métier sert les clients. Le mot-clé qui circule entre les couches, c'est « service ».

3.2 L'exemple fil rouge : le permis de stationnement

Le cours utilise un exemple complet (slides 31-39) : une municipalité délivre un permis de stationnement à un citoyen. Voici le modèle simplifié, couche par couche :

Lecture pédagogique du modèle, de haut en bas :

  1. Le parcours citoyen : consulter les infos → fournir les infos → payer → recevoir le permis. C'est l'expérience visible du service.
  2. Les services métier (Information provision, Intake, Payment, Permit provision) : l'interface entre le citoyen et l'administration.
  3. Le processus métier interne « Provide Parking Permit » et ses activités (Show product information, Intake application, Assess application, Receive payment, Provide permit). Remarque : Assess application (vérifier l'éligibilité) est interne — le citoyen ne le voit pas !
  4. Les applications : front-office orientées citoyen (Portal citizens, Web intake, Payment) et back-office orientées agents (CMS, Backoffice citizens affairs, Basic information registers, DMS).

3.3 Les 2 problèmes que le modèle révèle (slides 38-39)

⚠ Problème 1 : architecture en silos
Le processus repose sur plusieurs SI distincts (portail, formulaire, paiement, gestion des dossiers, DMS, registres) → intégrations complexes, transferts de données multiples, risques d'erreurs et incohérences.
⚠ Problème 2 : mauvaise expérience utilisateur
Le parcours citoyen traverse plusieurs interfaces (portail, formulaire, paiement). Si ces systèmes sont distincts, le citoyen est redirigé d'un système à l'autre → expérience fragmentée ou confuse.
💡 Pourquoi c'est puissant
C'est exactement l'intérêt de l'EA : le modèle rend les problèmes visibles (silos, fragmentation) avant qu'on investisse. On retrouve la fonction « prédictive » d'un bon modèle (chapitre 1).

✏️ Vérifie ta compréhension
1. Quelle est la relation entre TOGAF et ArchiMate ?
✔ Les deux sont maintenus par l'Open Group. TOGAF structure la démarche (roue ADM), ArchiMate exprime les modèles des phases B, C, D. Analogie ch. 3 : la méthode de Bruce Silver (démarche) vs la notation BPMN (langage).

✔ Définition exacte du cours. Mémo : technologie → sert → applications → servent → métier → sert → clients.
Section 4

La couche Métier : les éléments ★★★

ArchiMate classe chaque élément dans une des 3 colonnes : la structure active (qui agit ?), le comportement (que fait-on ?) et la structure passive (sur quoi agit-on ?). Cette grille est la clé pour tout mémoriser.

Éléments jaunes = couche métier ◻ coins carrés = structure active ▢ coins arrondis = comportement ▤ bandeau = structure passive
Structure active — « qui ? »
Acteur métier (Business actor)

Entité métier capable d'exécuter un comportement. Concret : humains, départements, unités d'affaires. Nom = un nom commun ou propre.

Ex : Greg, Centre de contact ArchiSurance, ABC Corporation

Rôle métier (Business role)

Responsabilité d'exécuter un comportement spécifique, à laquelle un acteur peut être assigné. C'est le rôle qui reçoit les processus/fonctions ; l'acteur assigné au rôle les exécute au final.

Ex : Analyste sinistres voyage, Spécialiste, Fournisseur

Collaboration métier

Agrégat de deux ou plusieurs éléments de structure active interne qui travaillent ensemble pour un comportement collectif. Souvent temporaire : pas besoin d'un statut officiel permanent (≠ département).

Ex : « Évaluation des réclamations à haut risque » = Spécialiste + Représentant du service clientèle

Interface métier

Point d'accès où un service métier est mis à disposition de l'environnement. Souvent appelée un canal (téléphone, internet, guichet…). Un même service peut être exposé via plusieurs interfaces.

Ex : Téléphone, E-mail, Chat en ligne

⚠ Piège d'examen n°1 : acteur ≠ rôle
L'acteur = l'entité concrète (Greg, le département X). Le rôle = la responsabilité abstraite (Analyste sinistres). Un acteur peut être assigné à plusieurs rôles, et un rôle peut être tenu par plusieurs acteurs. À l'examen : « Greg remplit le rôle d'Analyste » → relation d'assignation de l'acteur vers le rôle. Astuce : si on peut dire « c'est le métier/la casquette » → rôle ; « c'est la personne/l'organisation » → acteur.

L'exemple ArchiSurance (slide 48) — à savoir raconter

  • Le Centre de contact ArchiSurance (acteur) est composé de trois acteurs : Greg, Joan, Larry.
  • Il dispose de trois interfaces : Téléphone, E-mail, Chat en ligne.
  • Greg est assigné au rôle « Analyste des demandes d'indemnisation voyage », Joan au rôle « Spécialiste produits habitation », Larry au rôle « Représentant du service clientèle ».
  • Les deux premiers rôles sont des spécialisations du rôle « Spécialiste ».
  • « Évaluation des réclamations à haut risque » = collaboration entre « Spécialiste » et « Représentant du service clientèle ».
Comportement — « quoi ? »
Processus métier

Séquence de comportements métier qui atteint un résultat spécifique (produits ou services définis). Regroupe le comportement par résultat à produire. Reste une boîte noire : le détail se modélise en BPMN.

Ex : Accepter le sinistre, Attribuer le sinistre, Payer la réclamation

Fonction métier

Collection de comportements métier basée sur un ensemble de critères choisis — typiquement les ressources et compétences requises. Regroupe par savoir-faire, pas par résultat.

Ex : Gestion des sinistres, Gestion de la clientèle, Traitement des paiements

Interaction métier

Unité de comportement collectif exécutée par (une collaboration de) deux rôles ou plus. C'est le pendant « comportement » de la collaboration (structure).

Ex : Statuer sur une réclamation à haut risque (2 personnes obligatoires, anti-fraude)

Événement métier

Élément de comportement qui dénote un changement d'état de l'organisation. Instantané (pas de durée !). Peut venir de l'extérieur ou de l'intérieur. Nom = verbe au passé (« claim received »).

Ex : Sinistre déclaré → déclenche « Accepter le sinistre »

Service métier

Comportement métier explicitement défini et exposé. Il expose la fonctionnalité des rôles/collaborations à leur environnement ; on y accède via une ou plusieurs interfaces. Doit être une unité de comportement utile du point de vue de l'environnement (du client !). Nom = idéalement un verbe en « -ing » ou avec « service ».

Ex : Traitement des sinistres (Claims processing), Intake, Payment

⚠ Piège d'examen n°2 : processus ≠ fonction
Les deux décrivent du comportement interne, mais le critère de regroupement diffère : le processus regroupe ce qui est nécessaire pour réaliser un produit/service (logique de résultat, séquence) ; la fonction regroupe selon les ressources, compétences, connaissances requises (logique de savoir-faire, stable). Ex : la fonction « Gestion des sinistres » contient les processus « Accepter le sinistre », « Attribuer le sinistre »…
⚠ Piège d'examen n°3 : service ≠ interface
Le service = le comportement exposé (ce qu'on offre). L'interface = le point d'accès / canal par lequel on y accède (comment on l'atteint). « Traitement des sinistres » est un service ; « Téléphone » est une interface. Un même service peut passer par plusieurs interfaces, et une interface peut exposer plusieurs services.

L'exemple « Gestion des sinistres » (slide 51) — le scénario type de l'examen

📖 Scénario à maîtriser
  • La fonction métier « Gestion des sinistres » est composée de plusieurs processus métier et d'une interaction métier. Elle réalise le service métier « Traitement des sinistres ».
  • L'événement « Sinistre déclaré » déclenche le processus « Accepter le sinistre », qui déclenche « Attribuer le sinistre ».
  • Selon le type de réclamation : processus « Statuer sur une réclamation standard » ou interaction « Statuer sur une réclamation à haut risque » (2 personnes obligatoires → anti-fraude).
  • Après évaluation : « Informer le client » et « Payer la réclamation » en parallèle, puis « Clôturer la réclamation ».
Structure passive — « sur quoi ? » (+ le Produit)
Objet métier (Business object)

Concept utilisé dans un domaine métier particulier. Modélise un type d'objet (comme une classe UML / un type d'entité du ch. 2), dont plusieurs instances existent. Vision métier de l'information, indépendante de l'informatique.

Ex : Réclamation, Police d'assurance

Contrat

Spécification formelle ou informelle d'un accord entre un fournisseur et un consommateur : droits, obligations, paramètres fonctionnels et non-fonctionnels. C'est une spécialisation de l'objet métier. Peut être un SLA.

Ex : Police d'assurance, Contrat « Conduisez bien et économisez »

Représentation

Forme perceptible de l'information portée par un objet métier. Le support concret : document, message… Classable par médium (électronique, papier, audio) ou format (PDF, HTML…).

Ex : Formulaire de soumission, Lettre de réclamation

Produit

Collection cohérente de services et/ou d'éléments de structure passive, accompagnée d'un contrat, offerte comme un tout à des clients (internes ou externes). Couvre les produits intangibles (services, information) comme physiques.

Ex : produit « Assurance » = contrat « Police » + service « Service client »

⚠ Piège d'examen n°4 : objet métier ≠ représentation ≠ objet de données
Trois niveaux pour « la même » information : l'objet métier (le concept : la Réclamation) peut être réalisé par une représentation (la forme perceptible : la lettre de réclamation papier) et/ou par un objet de données (couche application : l'enregistrement Réclamation dans la base). Exemple du cours : l'objet « Réclamation » a 3 représentations selon l'étape du processus — Formulaire de soumission, Résumé du dossier, Lettre de réclamation.

L'exemple « Produit Assurance » (slide 54)

Le produit « Assurance » comprend le contrat « Police d'assurance » et le service « Service client », qui agrège 4 services : Demande, Renouvellement, Traitement des sinistres, Recours. Le produit « Assurance automobile » est une spécialisation de « Assurance », avec en plus le service « Conduisez bien et économisez » et son contrat associé. → Repère les relations : composition/agrégation + spécialisation.

✏️ Vérifie ta compréhension — couche métier
1. « Le guichet de la gare » et « le vendeur de billets » : comment les modéliser ?
✔ Le guichet est un point d'accès au service (comme téléphone/e-mail chez ArchiSurance) → interface. « Vendeur de billets » décrit une responsabilité qu'on peut assigner à Paul ou Marie → rôle. Paul, lui, serait un acteur.
2. « Gestion de la clientèle » regroupe tout ce qui touche à la relation client, quel que soit le produit concerné. C'est…
✔ Pas de résultat spécifique ni de séquence : on regroupe par savoir-faire → fonction. Les processus (« Traiter une plainte ») vivent à l'intérieur de la fonction.
3. Pourquoi « Statuer sur une réclamation à haut risque » est-elle modélisée comme une interaction et non un processus ?
✔ Interaction = comportement collectif de ≥ 2 rôles (via une collaboration). Le motif du cours : deux personnes impliquées pour minimiser le risque de fraude.
4. Vrai ou faux : « Un événement métier a une durée, comme un processus. »
✔ Faux : contrairement aux processus, fonctions et interactions, l'événement est instantané — il n'a pas de durée. Même logique qu'en BPMN (ch. 3) : « atomique, instantané ».
Section 5

La couche Application : les éléments ★★★

Bonne nouvelle : la couche application est le miroir de la couche métier. Mêmes trois colonnes, mêmes logiques — mais tout est logiciel et les noms commencent par « application ».

Structure active — « quelle appli ? »
Composant applicatif (Application component)

Encapsulation de fonctionnalité applicative alignée sur la structure d'implémentation, modulaire et remplaçable. Unité autonome : déployable, réutilisable, remplaçable indépendamment. Sa fonctionnalité n'est accessible que via ses interfaces.

Ex : Devis (Quotation), Achat (Purchase), CRM, DMS

Collaboration d'application

Agrégat de deux composants applicatifs ou plus qui coopèrent pour un comportement collectif. Typiquement logique ou temporaire : n'existe pas comme entité séparée dans l'entreprise.

Ex : « Vente d'assurances voyage en ligne » = Devis + Achat

Interface d'application

Point d'accès où des services d'application sont mis à disposition d'un utilisateur, d'un autre composant, ou d'un nœud. Deux visages : GUI (vers l'humain) ou API (vers une autre appli).

Ex : Interface de services Web (API) servant le composant « Site Web de voyage »

Comportement — « que fait l'appli ? »
Fonction d'application

Comportement automatisé qui peut être exécuté par un composant applicatif. Comportement interne ; s'il est exposé, c'est via des services. Peut réaliser un ou plusieurs services d'application.

Ex : Transférer le devis, Finaliser l'achat, Comptabilité

Interaction d'application

Unité de comportement collectif exécutée par (une collaboration de) deux composants ou plus — p.ex. le schéma de communication entre eux.

Ex : « Souscrire une assurance voyage » (Purchase Travel Insurance)

Processus d'application

Séquence de comportements applicatifs qui atteint un résultat spécifique. Comportement interne requis pour réaliser un ensemble de services.

Ex : « Obtenir une assurance voyage », Claims adjudication

Événement d'application

Élément de comportement applicatif qui dénote un changement d'état. Sans durée, comme au niveau métier. Nom = verbe au passé.

Ex : « Demande de devis (reçue) » déclenche le processus d'application

Service d'application

Comportement applicatif explicitement défini et exposé. Réalisé par une ou plusieurs fonctions d'application, accessible via des interfaces. Doit être utile en soi pour ses utilisateurs (une unité de comportement significative pour l'environnement).

Ex : Obtenir un devis, Souscrire l'assurance proposée

Structure passive — « quelles données ? »
Objet de données (Data object)

Données structurées pour un traitement automatisé. Doit être un morceau d'information autonome, avec un sens clair pour le métier (pas seulement pour l'application). Peut réaliser un objet métier. Lien direct avec le chapitre 2 : c'est ce qu'on retrouve dans les tables de la base de données !

Ex du cours : « Devis d'assurance en ligne » composé de « Prix proposé » + « Conditions générales » + « Certificat d'authenticité » ; « Devis assurance auto » et « Devis assurance voyage » en sont des spécialisations (voyage contient en plus « Itinéraire acheté »)

  • La fonction « Souscrire une assurance voyage » se compose de « Transférer le devis » (qui réalise le service « Obtenir un devis ») et « Finaliser l'achat » (qui réalise « Souscrire l'assurance proposée »). Ces fonctions modélisent le comportement des composants « Devis » et « Achat ».
  • L'événement « Demande de devis » déclenche le processus « Obtenir une assurance voyage », pris en charge (servi) par les deux services.
  • Côté données : « Devis d'assurance en ligne » est composé de 3 objets ; les devis auto et voyage en sont des spécialisations.
✏️ Vérifie ta compréhension — couche application
1. Une API REST exposée par le composant « Paiement » vers d'autres applications : quel élément ?
✔ L'API est un point d'accès → interface. Ce qu'on obtient via l'API (« traiter un paiement ») est le service. Retiens : interface = GUI (vers l'humain) ou API (vers une appli).
2. Quelle propriété définit le composant applicatif ?
✔ « Modulaire et remplaçable » + encapsulation. L'option 2 décrit l'événement, l'option 3 la collaboration.
3. Dans l'exemple du cours, qu'est-ce qui « réalise » le service d'application « Obtenir un devis » ?
✔ Schéma canonique : le composant est assigné à la fonction, la fonction réalise le service, le service est exposé via l'interface. Grave-toi cette chaîne !
4. Vrai ou faux : « Un objet de données peut réaliser un objet métier. »
✔ Vrai — c'est même LE lien inter-couches de la structure passive : l'objet métier « Réclamation » (concept) est réalisé par l'objet de données « Réclamation » (enregistrement structuré) et/ou par une représentation (document).
Section 6

Les 12 relations ArchiMate ★★★

Les relations sont le squelette de tout modèle ArchiMate — et la source n°1 d'erreurs à l'examen. Elles se classent en 4 familles. Pour chacune : la notation, la définition du cours, et une phrase-mémo.

Famille 1 — Relations structurelles

RelationNotationDéfinition & mémo
Composition Un élément consiste en un ou plusieurs autres concepts. Losange plein côté « tout ». Lien fort : la partie n'existe pas sans le tout. Mémo : « est composé de » — le losange plein « avale » ses parties.
Agrégation Un élément regroupe plusieurs autres concepts. Losange creux. Lien faible : les parties peuvent exister indépendamment. Mémo : le produit « Assurance » agrège des services qui existent aussi seuls.
Assignation Allocation de responsabilité, exécution d'un comportement. Boule pleine côté « qui », flèche pleine côté « quoi ». Relie la structure active au comportement (ou l'acteur au rôle). Mémo : « Greg est assigné au rôle d'Analyste » ; « le composant Devis est assigné à la fonction Transférer le devis ».
Réalisation Une entité joue un rôle critique dans la création/réalisation d'une entité plus abstraite. Pointillés + triangle creux vers l'abstrait. Mémo : le concret réalise l'abstrait — le processus réalise le service, l'objet de données réalise l'objet métier.

Famille 2 — Relations de dépendance

RelationNotationDéfinition & mémo
Serving
(service)		 Un élément fournit sa fonctionnalité à un autre. Trait plein + pointe ouverte. Direction : du fournisseur vers le bénéficiaire. Mémo : le service d'application → sert → le processus métier. La flèche « donne ».
Accès Capacité d'un comportement (ou structure active) à observer ou agir sur un élément de structure passive. Pointillés fins. Mémo : le processus accède à l'objet métier (lecture/écriture) — pense aux data objects de BPMN.
Influence Un élément affecte la mise en œuvre ou l'atteinte d'un élément de motivation (objectif, principe…). Mémo : la seule relation tournée vers la motivation ; peut porter + ou −.

Famille 3 — Relations dynamiques

RelationNotationDéfinition & mémo
Déclenchement
(triggering)		 Relation temporelle ou causale entre éléments. Trait plein + flèche pleine. Mémo : l'événement « Sinistre déclaré » déclenche « Accepter le sinistre » — comme le flux de séquence en BPMN.
Flux (flow) Transfert d'un élément à un autre (information, biens…). Pointillés + flèche pleine. Mémo : « quelque chose circule » sans forcément déclencher — comme le flux de message en BPMN.

Famille 4 — Autres relations

RelationNotationDéfinition & mémo
Spécialisation Un élément est un type particulier d'un autre élément. Trait plein + triangle creux vers le générique. Mémo : « Assurance auto » est une sorte d'« Assurance ». C'est le « is-a ».
Association Relation non spécifiée, ou non représentée par une autre relation ArchiMate. Simple trait. Mémo : le joker — à n'utiliser que si rien d'autre ne convient.
Jonction Sert à connecter des relations du même type (séparer/rassembler des chemins). Mémo : le « gateway » d'ArchiMate — l'équivalent des branchements BPMN.
⚠ Pièges d'examen sur les relations
  • Réalisation vs spécialisation : même triangle creux, mais réalisation = trait pointillé (concret → abstrait), spécialisation = trait plein (sous-type → type).
  • Déclenchement vs flux : même flèche pleine, mais déclenchement = trait plein (cause/séquence), flux = trait pointillé (transfert).
  • Serving vs réalisation : le processus réalise le service (il le fabrique) ; le service sert son consommateur (il lui est utile). Fabricant → réalise ; fournisseur → sert.
  • Composition vs agrégation : plein = partie inséparable du tout ; creux = regroupement de parties autonomes.
  • Sens des flèches : serving part du fournisseur ; réalisation pointe vers l'abstrait ; assignation part de la structure active.
✏️ Vérifie ta compréhension — relations
1. « Le processus métier "Provide Parking Permit" _____ le service métier "Permit provision". »
✔ Le processus (concret, interne) réalise le service (abstrait, exposé). Pointillés + triangle creux vers le service.
2. « Greg remplit le rôle d'Analyste des sinistres. » Quelle relation entre l'acteur Greg et le rôle ?
✔ Acteur → rôle = assignation (allocation de responsabilité). La composition, c'était Centre de contact ⬥— Greg/Joan/Larry ; la spécialisation, c'était Analyste ▷ Spécialiste.
3. Une flèche en pointillés avec pointe pleine entre deux fonctions : « rapport mensuel » circule de l'une à l'autre. C'est…
✔ Pointillé + flèche pleine + « quelque chose est transféré » = flux. (Accès = pointillé fin + pointe ouverte, vers un élément passif.)
4. Le processus « Assess application » lit l'objet métier « Demande de permis ». Quelle relation ?
✔ Comportement ↔ structure passive = accès (lecture/écriture). Le serving relie des éléments qui se rendent service, pas des données.
Section 7

L'articulation inter-couches ★★★

C'est ici que tout se rejoint — et c'est le cœur des exercices de modélisation. Comment les couches se « parlent »-elles ? Avec seulement trois relations clés : serving, réalisation et accès.

Le pattern canonique (à connaître par cœur)

Lis ce schéma comme une histoire (de bas en haut) :

  1. Le composant applicatif (Web intake) est assigné à la fonction d'application — c'est lui qui l'exécute.
  2. La fonction réalise le service d'application — le comportement interne fabrique le comportement exposé.
  3. Le service d'application sert le processus métier — l'IT rend service au métier. ⬅ C'est LA flèche qui traverse les couches !
  4. Côté données : l'objet de données réalise l'objet métier, et le comportement y accède.
  5. Au niveau métier : l'acteur/rôle est assigné au processus, qui réalise à son tour le service métier offert au client.
💡 La règle d'or inter-couches
Entre deux couches, on retrouve presque toujours les mêmes verbes : la couche du dessous SERT (serving) la couche du dessus ; le concret RÉALISE l'abstrait ; la structure active est ASSIGNÉE au comportement ; le comportement ACCÈDE à la structure passive. Si tu maîtrises ces 4 verbes, tu peux justifier n'importe quelle flèche d'un modèle.
⚠ Erreurs de modélisation courantes (check-list avant de rendre ta copie)
  • ❌ Faire servir le métier vers l'application (le serving monte : app → métier, techno → app).
  • ❌ Confondre le sens de la réalisation (elle pointe vers l'élément le plus abstrait : service, objet métier).
  • ❌ Relier un acteur directement à un service d'application au lieu de passer par le processus ou une interface.
  • ❌ Utiliser une association partout par facilité — l'examinateur attend la relation précise.
  • ❌ Oublier que l'événement se connecte par du déclenchement, pas du serving.
  • ❌ Mettre un élément comportemental avec des coins carrés (ou l'inverse) — la forme fait partie de la sémantique !
✏️ Vérifie ta compréhension — inter-couches
1. Complète la chaîne : composant applicatif —(assignation)→ fonction d'application —(?)→ service d'application —(?)→ processus métier
✔ La fonction réalise le service (concret → abstrait), le service sert le processus (couche inférieure → supérieure).
2. Dans quel sens va la flèche serving entre couches ?
✔ Serving part toujours du fournisseur : techno → app → métier → client. Même logique que la définition des 3 couches (« soutient la couche métier »).
3. L'objet métier « Police d'assurance » et l'objet de données « Police d'assurance » (table SQL) : quelle relation ?
✔ Le concret (données structurées) réalise l'abstrait (concept métier). La flèche (triangle creux, pointillés) pointe vers l'objet métier.

Exercice 1 — QCM de synthèse (8 questions)

Série QCM chronométrée (vise ~8 minutes)
1.1 — Quel est l'ordre correct des premières phases de la roue ADM ?

1.2 — La phase « G. Gouvernance de mise en œuvre » consiste à…
✔ La 2e réponse décrit la phase E (Opportunités et solutions), la 3e décrit la phase H (Gestion du changement).

✔ Le portail est un logiciel modulaire → composant applicatif. Ce qu'il offre (« demande de permis en ligne ») est le service ; l'écran par lequel on y accède est l'interface (GUI).
1.4 — Quelle affirmation sur le service métier est correcte ?
✔ La 1re réponse décrit le processus, la 3e l'événement. Le service = comportement exposé et utile pour le consommateur.
1.5 — « Assurance habitation » par rapport à « Assurance » : quelle relation ?
✔ « est une sorte de » = spécialisation. Attention au piège : même triangle que la réalisation, mais trait plein.

✔ C'est justement l'inverse : la gestion des exigences est continue et centrale, elle interagit avec toutes les phases. (Lien ch. 2 : l'ingénierie des exigences n'est jamais « one shot ».)
1.8 — Quel élément appartient à la structure PASSIVE de la couche métier ?
✔ Passif = ce sur quoi on agit : objet métier, contrat, représentation. La collaboration est active, l'interaction est du comportement.

Exercice 2 — Question de situation (style « appliquer la théorie »)

📋 Énoncé

L'université UniCampus veut digitaliser l'inscription de ses étudiants. Aujourd'hui : le service inscriptions utilise un logiciel maison, la comptabilité utilise un ERP pour les paiements de minerval, et la bibliothèque a son propre système de création de comptes. L'étudiant doit s'adresser aux trois services séparément, et ses données sont réencodées trois fois.

a) Diagnostique le problème avec le vocabulaire du chapitre. b) Explique ce que l'architecture d'entreprise apporterait, en citant les phases TOGAF pertinentes. c) Quels sont les deux risques (vus dans l'exemple du permis de stationnement) que ce cas illustre ?

Voir la correction détaillée

a) Diagnostic. Les SI d'UniCampus sont organisés par domaine fonctionnel (inscriptions, comptabilité, bibliothèque) : ce sont des applications cloisonnées (silos). Or le processus « Inscrire un étudiant » est transversal : il traverse les trois domaines. Ce décalage impose des transferts de données multiples (réencodage ×3) → risques d'erreurs et d'incohérences.

b) Apport de l'EA. L'EA fournit un ensemble cohérent de descriptions pour gouverner l'évolution, et sert d'instrument de coordination vers la transformation. Concrètement, via l'ADM : phase B — modéliser le processus d'inscription as-is et cible ; phase C — cartographier les applications as-is (3 silos) et concevoir la cible (p.ex. un référentiel étudiant unique / des services d'application partagés) ; analyse de gap pour identifier les lacunes (processus, compétences, financières, matérielles) ; phases E-F — feuille de route et plan de migration (baseline → transitions → target) ; phase G — gouvernance pour garantir que les projets respectent l'architecture cible.

c) Les deux risques du cours. ① Architecture en silos : intégrations complexes, transferts multiples, incohérences de données. ② Mauvaise expérience utilisateur : l'étudiant est redirigé entre plusieurs interfaces → parcours fragmenté et confus.

Exercice 3 — Choisir le bon élément ArchiMate (6 items)

Pour chaque situation, quel élément ?
3.1 — « Le département des inscriptions d'UniCampus »
✔ Un département est une entité concrète capable d'exécuter du comportement → acteur (comme « Centre de contact ArchiSurance »).
3.2 — « Conseiller académique » (responsabilité que Mme Dupont et M. Martin exercent tous les deux)
✔ Une responsabilité à laquelle plusieurs acteurs sont assignés = rôle.
3.3 — « Dossier d'inscription » (le concept, indépendamment de sa forme papier ou numérique)
✔ Le concept métier = objet métier. Le formulaire PDF serait une représentation ; l'enregistrement en base serait un objet de données (qui réalise l'objet métier).
3.4 — « Paiement du minerval reçu » (déclenche la validation de l'inscription)
✔ Changement d'état instantané, nommé au passé, qui déclenche un processus → événement.
3.5 — « Guichet en ligne » par lequel l'étudiant accède au service d'inscription
✔ Point d'accès / canal = interface. Le service, c'est « Inscription » ; le guichet en ligne n'est que le chemin pour l'atteindre.
3.6 — « Gestion financière » (tout ce qui demande des compétences comptables, quel que soit le processus)
✔ Regroupement par compétences/ressources (et non par résultat) = fonction.

Exercice 4 — Modélisation guidée (le grand classique)

📋 Énoncé : « BiblioTech »

La bibliothèque universitaire offre à ses lecteurs un service de réservation d'ouvrages en ligne. Le processus interne « Traiter une réservation » est exécuté par le rôle Bibliothécaire (tenu par l'actrice Sofia). Il est déclenché par l'événement « Réservation soumise ». Le processus consulte l'objet métier « Catalogue ». Côté IT : le composant applicatif « BiblioApp » exécute la fonction d'application « Vérifier la disponibilité », qui réalise le service d'application « Consultation du stock » utilisé par le processus métier. Les données du catalogue sont stockées dans l'objet de données « Catalogue (DB) ».

Consigne : dessine le modèle ArchiMate sur papier (formes + couleurs + les 8 relations), puis compare.

Voir le modèle corrigé + les 8 relations justifiées

Les relations, une à une :

  1. Assignation Sofia → Bibliothécaire : l'acteur est assigné au rôle (boule + flèche pleine).
  2. Assignation Bibliothécaire → « Traiter une réservation » : le rôle exécute le processus.
  3. Déclenchement « Réservation soumise » → processus : relation causale, trait plein + flèche pleine.
  4. Réalisation processus → service métier : le comportement interne fabrique le service exposé (pointillés + triangle creux).
  5. Accès processus → objet métier « Catalogue » : le comportement consulte la structure passive (pointillé fin).
  6. Serving service d'application → processus métier : LA relation inter-couches (pointe ouverte, du bas vers le haut).
  7. Réalisation fonction d'application → service d'application.
  8. Assignation BiblioApp → fonction : le composant exécute le comportement.
  9. Réalisation objet de données → objet métier (bonus : le lien passif inter-couches).

Auto-évaluation : ✔ formes correctes (carré = actif, arrondi = comportement, bandeau = passif) ? ✔ couleurs par couche ? ✔ sens du serving (app → métier) ? ✔ sens des réalisations (vers l'abstrait) ? Si oui : tu es prêt·e pour l'exercice d'examen.

Exercice 5 — Question ouverte de théorie (rédaction)

📋 Énoncé
« Expliquez pourquoi TOGAF et ArchiMate sont complémentaires, en illustrant votre réponse avec les phases B, C et D de l'ADM et les trois couches d'ArchiMate. » (≈ 10 lignes)
Voir les éléments de réponse attendus

Points à couvrir pour une réponse complète :

  • TOGAF = méthode : la roue ADM organise la démarche d'architecture (phases itératives, gestion des exigences au centre). Il dit quoi faire et dans quel ordre, mais ne fournit pas de notation pour dessiner les architectures.
  • ArchiMate = langage : notation graphique standardisée (éléments + relations + sémantique — comme BPMN pour les processus) pour exprimer les modèles. Il dit comment représenter, mais pas comment mener le projet.
  • La correspondance directe : la phase B (architecture métier) produit des modèles en couche métier ; la phase C (architecture des SI) en couche application ; la phase D (architecture technologique) en couche technologique. Pour chaque phase, ArchiMate permet de modéliser l'as-is et le to-be et de visualiser les gaps.
  • Bonus : les deux standards sont maintenus par l'Open Group ; sans langage unifié, chaque couche utiliserait sa propre notation, rendant invisibles les liens inter-couches (serving, réalisation) — or c'est précisément l'alignement métier-IT (ch. 1) qu'on veut voir.
